先说结论：前 AI 时代广域网上跑的主要是大量互相独立的流，有的弹性、可以等，有的跟着用户的作息走，彼此叠加后整体比较平滑。三类 AI 业务各自打破了其中一部分：

- 跨 DC 数据并行变成"少数几条大流，周期性地同时爆发"。
- 多 region 推理分发的流量跟着 GPU 的空闲情况走，不再只跟着用户走。
- agent 对外调用（也就是你说的出站调用）变成"一串前后依赖的小调用，而且很多去往外部"。

GGN 论文引言也写了这个变化：AI/ML 训练带来了"unprecedented demand"（前所未有的容量需求），与以往"Internet-delivered services and media streaming"（互联网服务和流媒体）时代的需求"significantly different"（显著不同）。

四类流量的形态对比

维度: 流的数量和大小
云时代（后端复制 + 用户流量）: 数百万条独立的流，单条不大（后端复制单条较大，但数量多、时间分散）
跨 DC 数据并行: 只有少数几条大流，固定在两个 DC 之间（比如贵安 ↔ 深圳），单对 DC 就要 Tbps 级
多 region 推理分发: 大量小请求：32K token 的 prompt 文本只有百 KB 级；响应是逐 token 流式返回，一个连接持续几秒到几分钟
agent 对外调用: 大量小调用。每个 agent 任务要调几十到上百次模型、工具和其他 agent
────────────────────────────────────────
维度: 时间形态
云时代（后端复制 + 用户流量）: 用户流量跟着时区昼夜起伏；后端复制可以排队、错峰
跨 DC 数据并行: 按训练步周期性地开关：计算阶段几乎没有流量，同步阶段一下子打满链路，峰均比高（你们 v5 测算为 16～60）。训练任务一跑几周到几个月，没有昼夜规律
多 region 推理分发: 仍然有昼夜规律，但流量去哪个 region 由 GPU 余量决定
agent 对外调用: 由模型的决策随机触发，突发、难以预测
────────────────────────────────────────
维度: 流之间是否同步
云时代（后端复制 + 用户流量）: 互相独立，统计上会互相抵消（统计复用）
跨 DC 数据并行: 高度同步：所有流在同一时刻开始，最慢的那条流决定这一步什么时候结束
多 region 推理分发: 基本独立
agent 对外调用: 同一个任务里的调用是串行依赖的，前一次的结果决定下一次调什么；也有并行调用多个工具再汇总
────────────────────────────────────────
维度: 方向
云时代（后端复制 + 用户流量）: 下行为主
跨 DC 数据并行: 双向对称
多 region 推理分发: 下行为主，但每次请求的字节数很小
agent 对外调用: 上行可能更大：无状态 API 每次调用都要把完整上下文重发一遍，请求大小随对话轮数增长；响应只是 token，反而更小
────────────────────────────────────────
维度: 衡量指标
云时代（后端复制 + 用户流量）: 平均吞吐（后端）；平均时延（用户）
跨 DC 数据并行: 每一步的完成时间，由尾部时延和最慢的流决定
多 region 推理分发: 首 token 时延（TTFT），跨 region 会多一个往返时延
agent 对外调用: 端到端的累积时延：每次调用的时延串联相加
────────────────────────────────────────
维度: 对丢包和抖动的敏感度
云时代（后端复制 + 用户流量）: 后端不敏感，可以重传、降速
跨 DC 数据并行: 很敏感：一条流卡住，全体都要等
多 region 推理分发: 中等：影响首 token 时延和流式输出是否顺畅
agent 对外调用: 中等：单次影响小，但调用次数多，会累积
────────────────────────────────────────
维度: 发送端是否可控（BwE 能不能管）
云时代（后端复制 + 用户流量）: 后端可控（B4 的前提）；用户流量部分可控
跨 DC 数据并行: 完全可控：集合通信库自己调度
多 region 推理分发: 部分可控：请求从互联网进来，分发和响应由 Google 控制
agent 对外调用: 大量不可控：调用的目标经常是第三方 API、别家云、MCP 服务
────────────────────────────────────────
维度: 可预测性
云时代（后端复制 + 用户流量）: 规律明显，按小时到天可以预测
跨 DC 数据并行: 单步内完全可预测：什么时候发、发多少都由训练计划决定。但从容量规划层面看，GGN 论文说"ML/AI-driven growth quickly outpaced projections"（AI 带来的增长很快超出了预测）
多 region 推理分发: 总量可以预测，但具体落到哪个 region 不好预测
agent 对外调用: 难以预测
────────────────────────────────────────
维度: 本地性
云时代（后端复制 + 用户流量）: 用户就近接入；后端按数据所在位置决定
跨 DC 数据并行: 固定的点对点
多 region 推理分发: 变差了：本地 GPU 满了就分发到更远的 region
agent 对外调用: 变差了：目标端点分散在各处

关键区别

1. 从"统计复用"变成"同步突发"（训练）。 云时代的海量独立流叠加后比较平滑，链路可以按平均值加一定余量来建；路由器缓存可以用 BDP/√n 估算，流越多需要的越少。跨 DC 训练只有几条大流而且同时爆发，这个"除以 √n"的折扣基本用不上，容量和缓存都要按峰值来考虑。

数量级举例：一个 1000 亿参数的模型，bf16 梯度约 200 GB，用 10 Tbps 传完要 0.16 s。你们 跨 DC.docx 图 3 的测算是：6 ms 时延下，效率损失控制在 10% 需要 24.42 Tbps，控制在 5% 需要 40.22 Tbps。

2. "带宽大的流量就能等"这个假设不成立了（训练）。 GGN 的优先级分档里，Tier 2 是"High-bandwidth, latency-insensitive"（大带宽、对时延不敏感），Tier 3 是"Bulk transfers"（批量传输），背后的假设是带宽大的流量都能等。

【推断】跨 DC 训练是"带宽大，同时对尾时延和丢包很敏感"，放进哪一档都不合适。

3. 流量跟着算力走，不再只跟着用户走（推理）。 云时代用户流量就近接入，规律跟着时区走。推理请求会被分发到有空闲 GPU、或者有可复用 KV cache 的 region，流量的去向取决于算力的余量。每次请求的字节数不多，但每个字节背后的算力价值很高。

4. 时延从"一次往返"变成"很多次往返串起来"（agent）。 网页请求通常是一两次往返。一个 agent 任务有几十到上百次前后依赖的调用，每次调用的时延直接累加到总时延里。

5. 上行变重（agent）。 传统 Web 是上行请求小、下行响应大。agent 用无状态 API 时，每次调用都重发完整上下文。服务端的 prompt 缓存只省计算，不省传输。所以请求可能比响应大得多。

6. 可控性两极分化。

- 训练流量完全可控，比 B4 当年的后端流量还要可控。
- agent 对外调用大量去往外部，和 B2 承载的互联网流量一样不可控。
- 推理分发介于两者之间。
